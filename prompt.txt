============================================================
PS-7.1 REQUIREMENTS
============================================================

The official challenge requires:

1. Instrumented agent wrapper

Capture:

- input received
- tool calls
- tool parameters
- tool responses
- intermediate observable reasoning/evidence where available
- final output

2. Decision path reconstructor

Given a session ID:

reconstruct the complete decision path as a structured timeline containing:

- input
- context retrieved
- tools called
- observable reasoning/evidence
- output

3. Decision summary generator

Use an LLM to produce a plain-English explanation suitable for:

- non-technical reviewer
- affected person

4. Redaction layer

Automatically redact PII from the stored decision path BEFORE persistence.

5. Queryability

Decision paths must be queryable by:

- session ID
- user ID
- time range

6. Success criteria

A three-step agent task:

retrieve
reason
decide

must be correctly reconstructed.

The summary must be accurate and readable.

PII must be correctly redacted before storage.

Audit records must be queryable.

7. Bonus

Challenge-response generator:

Given a decision path, generate a draft response to a regulatory challenge explaining the decision in terms of the specific data considered.

============================================================
IMPORTANT INTERPRETATION OF "REASONING"
============================================================

NEVER capture or expose hidden chain-of-thought.

Do not ask the LLM to reveal private chain-of-thought.

Do not store hidden reasoning tokens.

Instead capture observable decision evidence such as:

- retrieved documents
- policy references
- tool inputs
- tool outputs
- structured decision
- decision factors
- evidence
- model-generated concise reasoning summary

The audit trail should explain WHAT INFORMATION contributed to the decision and HOW THE DECISION LOGIC USED THAT INFORMATION, without exposing private chain-of-thought.

MILESTONE C — PII REDACTION
============================================================

Implement PII redaction BEFORE persistence.

This is a critical PS-7.1 requirement.

Create a dedicated PII service.

Do not scatter regexes throughout the application.

The service should expose a clean interface such as:

redact(value)

or an equivalent structured API.

============================================================
PII TYPES
============================================================

At minimum detect and redact realistic examples of:

- names
- email addresses
- phone numbers
- IP addresses
- physical addresses where feasible
- employee identifiers where appropriate
- government-style identifiers where appropriate

The exact implementation can use:

- Microsoft Presidio if compatible and justified
- deterministic regex-based recognizers
- a hybrid approach

Do not introduce an enormous dependency stack unnecessarily.

For this challenge, deterministic detection is acceptable where reliable.

The architecture must allow future replacement with a more sophisticated recognizer.

============================================================
REDACTION FORMAT
============================================================

Use consistent placeholders.

Examples:

John Smith
→ [REDACTED_NAME]

john@example.com
→ [REDACTED_EMAIL]

+91-9876543210
→ [REDACTED_PHONE]

Do not hash PII unless there is a specific reason.

The goal is actual redaction.

============================================================
STRUCTURED REDACTION
============================================================

PII redaction must work on:

- strings
- dictionaries
- lists
- nested structures

For example:

{
    "employee": {
        "name": "John Smith",
        "email": "john@example.com",
        "leave_balance": 12
    }
}

must become something like:

{
    "employee": {
        "name": "[REDACTED_NAME]",
        "email": "[REDACTED_EMAIL]",
        "leave_balance": 12
    }
}

Non-PII decision evidence must remain intact.

This is extremely important.

Do NOT redact the entire event.

============================================================
REDACTION GUARANTEE
============================================================

The persistence service must enforce the boundary:

Raw Event
    ↓
PII Redactor
    ↓
Sanitized Event
    ↓
Repository

There must be no code path where raw events can accidentally bypass the redaction layer.
